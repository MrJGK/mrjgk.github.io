Priority when the network is busy.

This project explores a simple access policy for a shared lab network. When the configured utilization threshold is reached, high-priority devices remain allowed while low-priority devices receive a RESTRICT decision. When utilization falls below the threshold, all devices return to ALLOW.

The prototype began as an additional module for the Network Monitoring and Visualization System and is being developed separately so the decision engine and controller-agent communication can be checked step by step.

Current scope: simulation. The prototype changes simulated access state and records decisions. It does not change Windows network settings or enforce real internet restrictions.

Target network scenario

  • 15 devices connected through a LAN switch.
  • 2 high-priority devices and 13 low-priority devices.
  • A Windows computer acts as the controller.
  • Development and testing currently take place on a laptop, before lab integration.

The access policy

The configured congestion threshold is 80%. Device priority and current utilization determine the access decision.

Network utilizationHigh-priority devicesLow-priority devices
Below 80%ALLOWALLOW
80% or aboveALLOWRESTRICT
Controller timeoutThe simulated agent returns to ALLOW as its fail-safe state.

In this phase, ALLOW and RESTRICT are decision labels used by the simulation. They make it possible to test policy changes before implementing an enforcement mechanism.

Implemented features

  • Priority engine. Represent each device with its priority and evaluate an ALLOW or RESTRICT decision.
  • Configuration file. Store device identifiers, addresses, priorities, and the controller flag in JSON.
  • Manual controller. Enter a utilization value from 0 to 100 to check normal and congested conditions.
  • Automatic controller. Sample traffic counters with psutil and report speed, calculated utilization, and access decisions.
  • Simulated client agent. Receive controller decisions over local HTTP and update simulated access state.
  • Transition logging. Record state changes such as ALLOW to RESTRICT, including their reason.
  • Timeout fail-safe. Return the simulated agent to ALLOW if controller updates stop.
  • Input checks. Validate configured device priority and utilization input.

Measurement boundary: the laptop prototype observes counters available on the controller computer. Measuring utilization for the entire switched lab network remains part of the integration work.

How the controller and agent work

  1. Load the device configurationRead the device list, identify the controller, and separate high- and low-priority devices.
  2. Get a utilization valueUse manual input for predictable policy tests or the automatic monitor’s calculated value.
  3. Evaluate the thresholdCompare utilization with 80% and determine which device states should change.
  4. Send the decisionThe controller sends an ALLOW or RESTRICT instruction to the simulated agent.
  5. Update and record the stateThe agent changes its simulated access state and logs the transition.
  6. Recover if communication stopsIf the controller times out, the agent restores ALLOW and records the fail-safe reason.

Observed simulation sequence

Local testing showed the simulated agent receiving ALLOW and RESTRICT decisions, logging transitions in both directions, and returning from RESTRICT to ALLOW after a controller timeout.

Progress & next steps

Working so far

  • The manual controller demonstrates the 80% rule and priority-based decisions.
  • The automatic controller reports sampled traffic and calculated utilization.
  • The simulated agent receives and records ALLOW and RESTRICT changes.
  • A controller timeout restores the agent’s ALLOW state.

Work still ahead

  • Integrate an appropriate source of utilization data for the full lab network.
  • Test controller-agent communication across the lab’s devices.
  • Define and implement actual access enforcement as a separate stage.
  • Add startup and recovery behavior for the controller.
  • Connect the module to the broader monitoring dashboard.

Boot-time startup, real network enforcement, and a completed lab deployment are future work.

What this prototype demonstrates

The current result is a working foundation for priority-based decisions: configuration, utilization input, rule evaluation, controller-agent communication, logging, and timeout recovery.

It provides a way to check the intended behavior before connecting real enforcement and network-wide monitoring. It also develops practical experience with Python, configuration design, and communication between separate processes.
